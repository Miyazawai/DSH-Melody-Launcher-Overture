# v1.0.2 — 下载 DSH 版本：这回是真修好了

一句话版本：**v1.0.1 说修好了「卡在 82%」，其实没修好。这一版修好了，而且原因跟用哪个源没关系。**

## 上一次为什么是空的

两个错叠在一起。

一个是 v1.0.1 给 pnpm 进程设了 `npm_config_registry` 环境变量。pnpm 11 不读这个变量。同一台机器上跑同一条命令，设了它日志里还是 `registry.npmjs.org`，只有改成 `--registry=` 旗标（或者写进 `.npmrc`）才会真的换源。那版改动唯一生效的部分是代理，代理走环境变量 pnpm 是认的。

更要命的是超时。那条 `pnpm add` 一直带着 `--fetch-timeout=30000`，而这个数限的是**整个请求**跑完的时间，不是「多久没数据算卡住」。DSH 0.1.7 的依赖里多了一个 `@deepseek-ai/libreoffice-kit-win32-x64`：

- 压缩包 121,492,977 字节（115.9 MB），解包后 325 MB
- 本机实测到镜像 CDN 的速度 610 KB/s，光下这一个包就要 190 秒

30 秒的线摆在那里，换成官方源、镜像源、任何源都是同一个结果。所以进度条爬到八十多趴住不动，几秒后抛「代码 1」。之前把它归给「漏配镜像源」是想当然了，换源只是让同一面墙早一点撞上。

## 改了什么

- registry 改用 `--registry` 旗标下发，代理继续走环境变量。
- 那条命令的 `--fetch-timeout` 从 30 秒放到 600 秒。

## 验证做到哪一步

用启动器改完之后那串一模一样的参数，在本机临时目录里跑完整的 `pnpm add @deepseek-ai/dsh@0.1.7-rc.1`：`Done in 1m 1.8s`，330 MB 依赖落盘，`.bin` 里 `dsh` 启动入口齐全。测试 861 条全过。

没做到的是：拿打好的 v1.0.2 便携版 exe 点一遍界面里的下载按钮。命令行这条路已经通了，界面那条链路上面还套着进度显示和入口重建，如果你还是撞到失败，把报错窗口里「运行环境」那一段整块贴过来。

## 你要做什么

装这个 exe 覆盖旧的就行，整合包数据不用动。之前下失败的那个版本重新点一次下载：缓存里已经下成的包不会重下，那个 116 MB 的二进制会重来一遍，按我这台的网速等一分多钟，你那边可能要几分钟。

便携版没有代码签名，SmartScreen 拦的时候确认来源是本仓库，再选「更多信息 → 仍要运行」。

## 顺带说一句

装插件和技能市场那两条链路也设了同样无效的 `npm_config_registry`，不过它们各自还有别的手段在传源，所以那两条到底走的哪个源我还没测实。如果你那边装插件经常很慢或者直接失败，在 issue 里说一声，那大概率是同一类问题。
